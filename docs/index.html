I knew nothing about text-to-speech when I started this.

Not the models. Not the terminology. Not the difference between a vocoder and a flow-matching diffusion transformer. I had never heard the word "IndicXlit" and I did not know what a mel spectrogram was.

What I had was a goal: build the best open-source TTS model for English.

That goal lasted about three days before I realized I was solving the wrong problem entirely.

This is the story of what actually happened — every wrong turn, every "wait, the metrics are lying to us," every 2 AM kernel crash on Kaggle. It ends with a system that scores 4.70/5.0 on a rigorous three-ASR evaluation rubric and beats every other open-source Hinglish-capable TTS model. Built with 14 lines of code. No training, no fine-tuning, no GPU budget.

The Pivot: Why Hinglish?

The original goal was English TTS. State of the art, best open-source model. Then I looked at what actually exists. English TTS is solved. Kokoro-82M produces natural English at 82M parameters. ElevenLabs does it commercially at scale. The field is crowded, mature, and the open/closed gap is shrinking fast.

Where is the real gap? India. 600 million Hindi speakers. Another several hundred million who speak Hindi mixed with English — what linguists call "Hinglish," what everyone in Indian cities just calls "talking."

Hinglish is not pidgin. It is not broken English. It is a fully developed code-switching register. A native speaker switches mid-sentence — sometimes mid-phrase — between Devanagari-script Hindi and Roman-script English:

"Boss को बता देना kal मैं leave पर रहूँगा, kuch personal काम है।"

One sentence. Three scripts. Two languages. How 100 million urban Indians text each other every day. No open-source TTS model handles it well. That became the problem I decided to solve.

The Audit: Testing What Already Existed

The first step was not building anything. It was measuring everything that already existed. I picked four candidate models and a 30-sentence eval set designed to stress every dimension of the problem:

The four models, run on free-tier Kaggle T4 GPUs (zero budget):

  2. Indic Parler-TTS (AI4Bharat, 880M params) — large, Indic-focused, text-description conditioned
  3. IndicF5 (AI4Bharat, 330M params) — flow-matching TTS, trained on Indic-script audio

IndicF5 did not sound worse than Kokoro on Hindi. It sounded better. The vowels were right, the aspiration was right, the rhythm was right. Something was wrong with the numbers. First lesson: on Hindi audio, auto-metrics lie.

Mistake #1: Single-ASR Scoring Is Broken for Hinglish

ASR models are trained on specific data distributions. A single model's failure becomes your score. Worse: when the TTS output is Devanagari but the reference text is Roman, character error rate comparison is meaningless. kya and क्या mean the same thing and sound identical, but CER between them is 1.0 — maximum error, as if they share no characters.

I spent a week trusting numbers that were measuring ASR bias, not model quality. The fix:

  1. Three-ASR consensus. AssemblyAI Universal-2 + Deepgram Nova-3 + Groq Whisper-large-v3. Majority vote. Each backend has different failure modes; the consensus is dramatically more reliable.
  2. Script normalization before scoring. Normalize both the reference text and the ASR transcript to unified Devanagari via IndicXlit before computing any error rate. office → ऑफिस. Now both sides speak the same script.

These two changes made the pipeline trustworthy. They also revealed how bad things actually were.

The Duration Bug: Why IndicF5 Was Producing Silence

With the corrected pipeline, IndicF5 re-scored at 2.13/5.0. Not because it sounded bad — because 21 of 30 outputs were truncated to 0.8–2.5 seconds when the sentence needed 3–6 seconds. I went looking for the bug.

Inside f5_tts/infer/utils_infer.py around line 451:

# Original IndicF5 code — this is the bug
ref_text_len = len(ref_text.encode("utf-8"))   # BUG
gen_text_len = len(gen_text.encode("utf-8"))   # BUG
duration = ref_audio_len + int(ref_audio_len / ref_text_len * gen_text_len / speed)

The model uses UTF-8 byte counts to estimate audio canvas time. The logic is reasonable — but breaks badly on script mixing:

  • Devanagari characters encode as ~3 bytes each in UTF-8
  • ASCII characters encode as 1 byte each

Reference clip transcript: 100 Devanagari chars × 3 bytes = 300 bytes → 3 seconds of audio. Generation text in Roman Hinglish: 100 chars × 1 byte = 100 bytes. Canvas allocated: 3s × (100/300) = 1 second. The model fills that 1 second correctly, then stops. The sentence is 66% truncated.

The fix — 4 lines:

# Count characters, not bytes
ref_text_len = sum(1 for c in ref_text if not c.isspace())
gen_text_len = sum(1 for c in gen_text if not c.isspace())
duration = ref_audio_len + int(ref_audio_len / ref_text_len * gen_text_len / speed)
print(f"DEBUG-PATCH: ref={ref_text_len} gen={gen_text_len} frames={duration - ref_audio_len}")

One क is one character. One k is one character. Canvas allocation becomes script-agnostic. After the patch, silence dropped from 20/30 to 16/30. But the overall score only moved from 2.13 to 2.20. Something else was wrong.

Mode C: The Undertrained Embedding Problem

With the correct canvas size, outputs were now the right length. But listen to what came out for Roman-script input:

Input: kal mujhe office jaana hai
ASR of output: ऐई अ एफे रेने आए

Syllabic noise. The Devanagari tokens in the same sentence (मुझे, जाना, है) rendered perfectly. Only the ASCII tokens produced garbage.

Root cause: IndicF5 was trained on Indic-script audio with Devanagari inputs. The embedding matrix has entries for every Unicode character, including A–Z. But those entries were never trained on meaningful data. The model receives a near-random vector for k and produces near-random acoustic output. Not a bug in the weights — a gap in the training distribution.

My first instinct was fine-tuning: train the ASCII embedding rows on Roman-script Hindi data. That would have taken weeks, cost hundreds of GPU-hours, and required labeled data I didn't have. I didn't fine-tune. I preprocessed instead.

The IndicXlit Fix: 14 Lines of Code Total

If the model can't handle ASCII input, don't give it ASCII input. IndicXlit is an open-source bidirectional transliteration library from AI4Bharat. kal → कल. office → ऑफिस. yaar → यार.

The key insight: the evaluation pipeline was already using IndicXlit to normalize transcripts for scoring. Apply the same normalization to the inputs before they reach the model.

def to_unified_devanagari(text: str) -> str:
    out = []
    for token in tokenize(text):
        if is_devanagari(token):
            out.append(token)           # pass through unchanged
        elif is_ascii_alpha(token):
            out.append(transliterate(token))  # Roman → Devanagari
        else:
            out.append(token)           # punctuation, digits: unchanged
    return "".join(out)

The preprocessing is symmetric: the same function normalizes both scoring reference and TTS input. No asymmetry between what the model gets and what the score measures.

When IndicXlit Gets It Wrong

IndicXlit is not perfect. On short tokens it applies English phonetics instead of Hindi:

TokenMeaningIndicXlit givesShould be
maiI (1st person)माई — "my" in Englishमैं
tuyou (informal)टू — "to" in Englishतू
aacomeएएआ
huam (1st person)हू (drops nasal)हूं

mai ghar aa raha hu (I am coming home) becomes माई घर एए रहा हू — four wrong words. The fix is a lookup table that intercepts before IndicXlit sees the token:

ROMAN_HINDI_FUNCTION_WORDS = {
    "mai": "मैं",   "tu": "तू",
    "aa":  "आ",    "hu": "हूं",
}

ENGLISH_LOAN_CANONICAL = {
    "office": "ऑफिस", "laptop": "लैपटॉप",
    "leave":  "लीव",   "boss":   "बॉस",
    # ... 36 entries total
}

The UTMOS Problem: When Auto-Metrics Lie on Hindi

Standard TTS evaluation uses UTMOS and SQUIM-MOS — automatic naturalness predictors trained on English studio speech. I recorded 8 human Hindi speakers reading the same evaluation sentences, then ran both human recordings and TTS outputs through both predictors:

SourceUTMOSSQUIM-MOS
IndicF5 TTS outputs3.2 – 3.83.5 – 4.1
Human native Hindi speakers1.7 – 2.41.8 – 2.6

The machine scored synthetic TTS as more natural than real human voices. This is predictor inversion. UTMOS and SQUIM are calibrated on English studio recordings; they penalize audio that doesn't match English studio speech patterns. A real Hindi speaker producing natural conversational speech gets penalized for not sounding like an English studio recording.

This means: every naturalness claim backed by UTMOS/SQUIM on Hindi is meaningless, and potentially inverted. If someone tells you their Hindi TTS scores 4.0 on UTMOS, they may be telling you it sounds worse than natural Hindi. I declared naturalness as ear-only for this project. No UTMOS. No SQUIM. Listen to the outputs.

The Kaggle Disasters

The project ran entirely on free-tier Kaggle T4 GPUs. Education included:

Disaster 1: The P100 trap. F5-family TTS models fail on P100 with cudaErrorNoKernelImageForDevice — the GPU is too old. I spent four hours debugging a failing kernel before discovering the machine shape. Always explicitly request T4.

Disaster 2: Kaggle Secrets don't work from CLI. API keys stored in the Kaggle vault are inaccessible to kernels pushed via kaggle kernels push. They only work when running from the web UI. Workaround: hardcode the HuggingFace token inline.

Disaster 3: "Successful" does not mean wavs were produced. The status API returns "status": "complete" regardless of what the kernel actually produced. Check output contents, not status codes.

Disaster 4: source .env doesn't propagate to subprocesses.

# Wrong — child process doesn't inherit:
source .env && python scoring/scripts/run_scoring.py

# Right:
export $(grep -v '^#' .env | xargs) && python scoring/scripts/run_scoring.py

Direction 1: Does the Model Actually Understand Phonetics?

After reaching 4.70, I got curious: does the model actually respond to fine phonetic markers — vowel length, aspiration, nukta (a dot that turns ज /j/ into ज़ /z/), the halant consonant cluster mark? I designed 18 clips: 6 phonetic distinctions × 3 variants each, bypassing preprocessing entirely — raw Devanagari fed directly to the model.

#Marker testedExample
1Vowel length (ि vs ी)short-i vs long-i
2Halant / schwa elision (् mark)खिल्ता vs खिलता
3Nukta (ज vs ज़)/j/ vs /z/
4Aspiration (ख vs क)/kʰ/ vs /k/
5Script registerRoman office vs ऑफिस vs आफिस
6Prosody / punctuationplain vs ellipsis + exclamation

The auto-metrics (ASR, F0 analysis) said: 3 of 6 distinctions produced different output. Then I listened. The ear said: 6 of 6. Three cases where auto-metrics failed:

  • Halant: ASR transcripts were identical, but the consonant cluster quality in खिल्ता was measurably different — spectral centroid shifted +112 Hz. ASR is lexical; it can't detect sub-phonemic consonant quality changes.
  • Aspiration: Clips were 0.65 seconds — below reliable Hindi ASR floor. Every backend produced garbage. But the difference between ख (aspirated) and क (unaspirated) was completely clear to the ear.
  • Prosody: मैं... बहुत... खुश हूं! and the plain version produced identical ASR transcripts. But the ellipsis+exclamation version was 44% longer (1.90s vs 1.32s), had slower pacing, and a rising terminal pitch. ASR can't measure prosody when words don't change.

Lesson: ASR-based metrics are lexical. For phonetic sensitivity — aspiration, tone, prosody, vowel quality — the ear is not just useful, it is irreplaceable.

Direction 2: Is the Model Thinking in Phonemes or Graphemes?

When the model produces क (Devanagari ka) and Roman k, are they routed through the same internal phoneme representation — or treated as unrelated graphemes that happen to produce similar sounds? I tested this with MFCC cosine similarity on the acoustic onset of /k/ across 32 clips.

Within Devanagari: /k/ across 8 vowel contexts showed mean pairwise MFCC similarity of 0.827. F0 varied systematically by vowel context (coarticulation — a real phonetic phenomenon). The model has phoneme-organized representations within Devanagari. It is not just memorizing grapheme→audio mappings independently.

Cross-script (Roman k vs क): Mean similarity delta = +0.052 above the unrelated-pairs baseline. Very weak. Two Roman inputs hit Mode C entirely — garbled output with F0 stuck at 93 Hz. The model has no phoneme access path for Roman input; it routes directly to noise.

Conclusion: phoneme-mediated within Devanagari, grapheme-bound for Roman. IndicXlit preprocessing works precisely because it routes everything through the Devanagari path, where phoneme organization exists.

IndicF5 + duration patch + IndicXlit preprocessing = working Hinglish TTS.

The package accepts any script-mixed Hinglish input, normalizes it to Devanagari, feeds it into the duration-patched model, and returns 24 kHz audio in any reference voice you supply.

from inference import load_model, synthesize
import soundfile as sf

model = load_model()  # downloads ~1.3 GB from HuggingFace on first run

REF_AUDIO = "data/reference_audio/hindi_ref.wav"
REF_TEXT  = open("data/reference_audio/hindi_ref.txt").read().strip()

# Pure Roman Hinglish
audio = synthesize(model, "yaar tu kal kya kar raha tha", REF_AUDIO, REF_TEXT)
sf.write("out.wav", audio, 24000)

# Mixed script
audio = synthesize(model,
    "Boss को बता देना kal मैं leave पर रहूँगा", REF_AUDIO, REF_TEXT)

# English with Indian named entities
audio = synthesize(model,
    "My friend Aishwarya from Chennai is visiting Bengaluru.", REF_AUDIO, REF_TEXT)

The Meta-Lesson

Three separate times on this project, auto-metrics pointed one direction and the human ear pointed another:

  1. Base model selection. Auto-rubric ranked Kokoro #1. Ear ranked IndicF5 better on Hindi naturalness. Trusting the ear flipped the model selection.
  2. Quality assessment. PESQ said quality improved with preprocessing. Ear said "still sounds like 90s TTS." Both true — they were measuring different things.
  3. Phonetic probe. Auto-metrics said 3/6 distinctions were sensitive. Ear said 6/6. Auto-metrics couldn't detect sub-phonemic changes or prosodic shifts without word changes.

When you are working on a language that wasn't in your metrics' training distribution, build in a human evaluation step before trusting any number. UTMOS was trained on English. AssemblyAI is optimized for English. MFCC cosine similarity doesn't know what Hindi sounds like. These are good tools — for what they were built for. "Works on English" does not mean "works on Hindi."

Measure your metrics before you trust your metrics.
